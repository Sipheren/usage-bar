# macOS architecture

How the macOS app (the reference implementation) is built. The rules every platform shares, such as
endpoints, the log format, de-duplication and prices, are in [DATA-SOURCES.md](../DATA-SOURCES.md).

The app is one SwiftPM package in `macos/` with three targets:

| Target | Kind | Holds |
|---|---|---|
| `UsageBarCore` | library | Everything testable: models, decoding, pace maths, formatting, pricing, the cost scanner, credential readers, fetch policy. No AppKit or SwiftUI. |
| `UsageBar` | executable | The app shell: status item, dropdown, Settings window, demo data, debug commands. |
| `UsageBarTests` | tests | XCTest suite against `UsageBarCore`, synthetic data only. |

`macos/scripts/build.sh` wraps the executable into `Usage Bar.app`, compiles the app icon from
`design/icon/AppIcon.icon`, writes `Info.plist` and signs it.

## Data flow

1. `AppDelegate` creates the `AppStore` (demo or normal) and the `StatusController`, then calls
   `store.start()`. With no saved settings it first runs `SignInDetector`, and the store saves settings
   holding only the accounts found (possibly none).
2. The store asks `AccountFetcher` to fetch each account. The fetcher reads the account's credential
   (read-only), calls the usage endpoint, and returns a `FetchReport`: a `UsageSnapshot` or an
   `AccountIssue`, plus the HTTP status and display details.
3. The store keeps one `AccountState` per account and saves it to
   `~/Library/Application Support/UsageBar/state.json`.
4. `StatusController` listens to the store. On any change it rebuilds the `MenuBarModel`, redraws the
   label, and resizes the dropdown's hosting view. SwiftUI views read the store directly.

## Polling and backoff

- A `.common`-mode timer ticks every 60 seconds, so it keeps firing while the menu is open. Each tick
  asks every account; each account fetches only when its own interval is due.
- `FetchPolicy.backgroundInterval` gives each account its interval: the refresh setting (1, 2, 5 or 10
  minutes; default 2), but at least 5 minutes for a token source. `FetchPolicy.isTokenSource` says which
  accounts those are: Claude Code always, and the Claude app when `AccountState.lastRoute` is "token".
  The OAuth usage endpoint allows only about 5 requests every few minutes, shared with Claude Code.
- `FetchPolicy.shouldFetch` decides every fetch:
  - Nothing fetches inside an account's Retry-After window.
  - Refresh Now always fetches outside that window.
  - The timer fetches once the interval has passed, less 30 seconds of slack for the tick.
  - A launch fetches only when the last attempt is a full interval old. The last attempt time is
    saved to disk, so relaunching costs no requests.
  - Opening the menu fetches when the last attempt is 2 minutes old, or the interval if shorter.
- On HTTP 429 (OAuth or claude.ai) the account waits `FetchPolicy.rateLimitWait`: Retry-After (seconds
  or an HTTP date) up to an hour, or 5 minutes when it is missing or 0. `AccountPresentation` keeps the
  last good numbers on screen and puts "Paused by rate limit · retrying 6:40 am" in the account header.
  With no data yet, it shows the error instead.
- Every 429 goes to the log (category `fetch`) with the account tag, the Retry-After header, the wait
  and the retry time.
- The Claude app fetch tries its claude.ai cookie first and its token only when the cookie doesn't
  work (`AccountFetcher.desktopCookieResultStands`).

## Cost scanner

`CostScanner` reads `~/.claude/projects/**/*.jsonl`, including subagent logs in subfolders.

- **Incremental.** For each file it keeps size, mtime, inode and the byte offset after the last
  complete line. It reads only new bytes. A file that shrank or changed inode is read again from
  the start. Files untouched for 31 days are skipped.
- **Pre-filter.** A line has to contain `"usage"` and `"assistant"` before any JSON decoding.
- **De-duplication.** The key is `message.id:requestId` (also `request_id`); without a request id it
  is `sessionId:message.id`. Claude Code writes several lines per message while streaming, and the
  later ones carry the full usage, so the scanner keeps the line with the largest token total (ties go
  to the later line). An "incomplete" line (no `stop_reason`, input > 0, output = 0, no cache fields)
  never replaces a complete one.
- **Cache writes.** It uses the 5-minute/1-hour split when `cache_creation` has it, and counts the
  aggregate `cache_creation_input_tokens` as 5-minute writes only when the split is missing.
- **Aggregation and pricing.** Records go into buckets per local day and model. `Pricing` turns them
  into US dollars; the store converts them to the chosen currency with the daily rate (none for USD).
- **Cache file.** `cost-cache.json` holds file positions and packed records: a 64-bit hash of the key,
  day, model index and five token counts. It holds no message content and no ids.
- The scan runs on a background queue with up to six files in parallel, at launch and every
  5 minutes. The dropdown shows "Counting…" until the first scan finishes.

## Menu bar rendering

`MenuBarModel.build` turns each shown account's snapshot into values (session, weekly, model weekly;
whichever are on). `MenuBarRenderer` draws the Claude spark (a vector path, 16 pt), then per account
an outlined tag and either text or stacked bars.

The image is always a template image, so macOS tints it for light and dark menu bars. The status item
redraws only when the label's content changes; it doesn't observe its own appearance (that caused a
redraw loop). Data older than 15 minutes draws at 50% opacity; an account with no data shows its tag
and "–".

## Settings storage

`AppSettings` is saved as JSON in the preferences under `settings.v1`. Decoding treats every field as
optional, so older saved settings keep working; settings without a readable account list fall back to
the original Personal + Work pair, as they always did. An empty list stays empty. There is no plain
`AppSettings()`: a first run uses `AppSettings(firstRunWith:)` and everything else names its accounts.
The cost currency defaults to AUD.
`applyMigrations()` runs once on settings saved before the current defaults: it switches the style to
Bars and moves a never-connected Claude app account to the Safari source. The exchange rates and
account emails have their own keys. No secret ever goes into
preferences.

## Demo mode

`--demo` or `USAGEBAR_DEMO=1` starts the store with built-in sample data and two accounts (Personal
and Work). `--demo-accounts N` starts it with 0 to 3 (Personal, Work, then a Claude app account), for
checking the UI at each count. It makes no network requests, reads no credentials or logs, and saves
nothing. The screenshots in `docs/images/` come from it.
